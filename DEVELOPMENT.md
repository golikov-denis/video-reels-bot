# Разработка и эксплуатация

## 1. Архитектура

### Управляющая часть — Vercel

Next.js, TypeScript и App Router. Здесь размещаются Telegram webhook, health-check, страница загрузки и API подготовки и завершения загрузки. Mini App, подписка и административная диагностика относятся к следующим этапам.

### Данные — Neon PostgreSQL и Backblaze B2

Neon хранит пользователей, идемпотентность Telegram updates, upload sessions и задачи. Drizzle ORM управляет схемой и SQL-миграциями. Telegram ID и размеры файлов хранятся как `bigint`; идентификаторы внутренних сущностей — UUID.

Приватный B2 bucket хранит исходники. Браузер загружает файл напрямую по короткоживущему подписанному PUT URL, минуя ограничения размера запроса serverless-функции. Lifecycle bucket удаляет объекты через один день. Production и Preview используют разные Neon branches, bucket, ключи и Telegram-ботов. Redis в MVP не добавляется без доказанной необходимости.

### Обработчик видео — следующий отдельный этап

Docker-контейнер на управляемой платформе, FFmpeg, PostgreSQL-очередь с lease/heartbeat, интерфейсы провайдеров распознавания, перевода и анализа, S3-совместимое хранилище и подписанные callback-запросы. Обработчик ещё не создан: запись `queued` не запускает вычисления и не обещает результат.

## 2. Поток загрузки

1. Webhook проверяет секрет Telegram и сохраняет `update_id`; повторный update не создаёт новую сессию.
2. `/start` создаёт или обновляет пользователя и upload session со сроком действия 30 минут. В базе сохраняется только SHA-256 хеш одноразового токена.
3. Страница `/upload/[token]` показывает состояние ссылки и принимает MP4, MOV, MKV или WebM размером до 2 ГБ.
4. `prepare` блокирует строку сессии, проверяет срок и метаданные, сохраняет server-generated object key и выдаёт подписанный PUT URL на 10 минут.
5. Браузер отправляет файл напрямую в B2 и показывает фактический прогресс XMLHttpRequest.
6. `complete` выполняет HeadObject, сравнивает размер и Content-Type с ранее проверенными метаданными, затем в транзакции создаёт единственную задачу `queued` и завершает сессию.
7. Повторный `complete` возвращает существующий job ID и не отправляет повторное Telegram-уведомление.

Если отправка ответа Telegram после `/start` не удалась, marker update удаляется, чтобы Telegram retry мог повторить обработку. Ранее созданные сессии при этом не отзываются автоматически; их действие ограничено TTL.

## 3. Правила процесса

Обычное изменение:

```text
изменение → npm run check → git status → проверка секретов → commit → push → Vercel READY → health-check
```

Рискованное изменение: отдельная ветка, Vercel Preview, тестовый бот, отдельные Neon branch и B2 bucket, реальная загрузка небольшого файла, затем merge в `main`.

Не использовать localhost.run, Cloudflare Tunnel, VPN-туннели или локальный polling-бот. Полный пользовательский сценарий проверяется только после публичного deployment.

Перед коммитом:

1. Выполнить `npm run check`.
2. Проверить `git status` и `git diff --check`.
3. Убедиться, что `.env`, реальные ключи, видео, архивы и временные снимки не попали в индекс.
4. Не сообщать об успешном deployment до фактического статуса READY.

## 5. Безопасность второго этапа

- Секрет webhook сравнивается на сервере с защитой от сравнения по времени.
- Токены Telegram, B2 и строки Neon используются только на сервере и не попадают в клиентский bundle.
- JSON ограничен по размеру; повреждённые и неподдерживаемые запросы отклоняются.
- Ошибки не возвращают stack trace, строки подключения или внутренние детали.
- Upload token содержит 32 случайных байта, передаётся в URL и хранится в базе только как хеш.
- Object key генерируется сервером; исходное имя файла не управляет путём в bucket.
- Размер и MIME-тип проверяются по фактическому объекту перед созданием задачи.
- Bucket приватный; CORS разрешает только PUT с точного origin приложения.
- Health-check сообщает только факт наличия конфигурации Telegram, не её значения.

Подписанная ссылка является bearer credential: её нельзя записывать в журналы, аналитику или публичные сообщения. На этом этапе нет проверки содержимого видео, длительности, антивирусного сканирования, rate limiting и пользовательской авторизации помимо одноразового токена.

## 6. Миграции, deployment и откат

1. Изменения схемы вносить в `src/db/schema.ts` и генерировать SQL через `npm run db:generate`.
2. Проверять сгенерированный SQL и включать его вместе с `drizzle/meta/` в тот же commit.
3. В Vercel Build Command override задано `npm run db:migrate && npm run build`. `npm run check` локально миграции не запускает, потому что локальные credentials могут отсутствовать.
4. Neon Preview branch создаётся интеграцией для ветки Git; переменные подключения действуют только внутри соответствующего Preview deployment.
5. Дождаться READY, проверить `/api/health`, реальный `/start`, загрузку и создание задачи.
6. Только после успешного Preview merge изменения в `main` и повторить production smoke-test.

Миграции должны быть обратно совместимы с предыдущей версией приложения. Откат deployment не откатывает уже применённую схему автоматически. Откат приложения: предыдущий READY deployment через Rollback либо проверенный `git revert`. Исправление схемы выполнять отдельной проверенной forward-миграцией; destructive changes требуют отдельного плана и резервной копии.

## 7. Мониторинг

- Внешняя проверка: `GET /api/health`, ожидается HTTP 200 и `status: "ok"`.
- Vercel: статус deployment, Build Logs, Function Logs и ошибки Runtime.
- Neon: активные branches, ошибки подключения и факт применения миграций.
- B2: наличие объекта, размер, Content-Type, CORS и удаление по lifecycle.
- Telegram: `getWebhookInfo`, включая `pending_update_count` и сведения о последней ошибке; токен в вывод не помещать.
- После появления обработчика: возраст задачи, lease/heartbeat, повторы, сбои callback и удаление файлов по TTL.

## 8. Известные ограничения

- Задача только ставится в очередь; FFmpeg и обработчик ещё не созданы.
- Проверяются метаданные объекта, но не кодек, длительность и фактическая структура видео.
- Нет Mini App, распознавания речи, перевода, субтитров, баннеров, истории, подписки и административной диагностики.
- Автоматические тесты используют моки; реальные Neon, B2 и Telegram проверяются отдельным smoke-test после deployment.
- Реальные платные smoke-тесты запрещены без отдельного явного разрешения владельца.

## 9. Стоимость

GitHub, Vercel, Neon и Backblaze B2 используются в рамках выбранных бесплатных тарифов; фактические лимиты аккаунтов и расход нужно проверять перед увеличением нагрузки. Видеообработчик и платные AI API ещё не подключены. Перед их созданием нужно зафиксировать тарифы, лимиты бесплатного использования и ожидаемую стоимость обработки одного видео. Платные ресурсы и API не активируются без подтверждения владельца.

## 10. Следующий проверяемый этап

После подтверждённой реальной загрузки: отдельный Docker-обработчик, безопасное получение исходника из B2, lease/heartbeat для задачи, FFmpeg-проба медиаданных и проверка длительности. Только после этого добавлять фактическую обработку, callback и переходы статусов. Платные AI-провайдеры и Telegram Stars остаются отдельными этапами с проверкой стоимости.
